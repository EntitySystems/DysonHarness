# UI

Landing project: [`src/Harness/Harness.UI`](../../src/Harness/Harness.UI) — Blazor Interactive Server (`net10.0-windows` on Windows, else `net10.0`), references `Harness.Engine` and (Windows only) `Harness.WindowsBrowser`. Shared host builder: `DysonUiWebHost` / `DysonUiWebHostOptions`. `DysonUiHost` is a hook, not a second engine — see [rules/rules_engine_ui.md](../../rules/rules_engine_ui.md).

## How to run

From repo root:

**Windows desktop shell (CefSharp):**

```bash
dotnet run --project src/Harness/DysonHarness.UI.Windows
```

If the circuit dies, F5 or right-click “Reload page” reloads the loopback page in-process (new circuit, same runtime).

**Browser-based Blazor (all platforms):**

```bash
dotnet run --project src/Harness/Harness.UI --launch-profile http
```

Debug/Development binds **http://localhost:5181** (`Properties/launchSettings.json` `http` / `https` profiles; VS F5 and `dotnet run` load them). `DysonUiWebHost` also binds 5181 when `ASPNETCORE_ENVIRONMENT=Development` and no URL was passed, so `dotnet run --no-launch-profile` does not fall through to Kestrel's :5000. The installed Windows shell (`DysonHarness.exe`) is not on 5181: `DysonHarness.UI.Windows/App.xaml.cs` passes `http://127.0.0.1:0` (ephemeral loopback). Published Linux/macOS `Harness.UI` is Production and keeps the Kestrel default http://localhost:5000. Do not stop `DysonHarness.exe` to verify a debug build. Pass `--urls http://localhost:5181` when you want the debug port explicitly.

Or open the solution and set **DysonHarness.UI.Windows** (Windows) or **Harness.UI** as the startup project. The app uses Interactive Server rendering globally. F5 on `Harness.UI` uses the `http` profile (5181).

DI: `AddDysonHosting` + `AddDysonLocalDb` (registers `IDyson*Repository` / `DysonDbContext` factory), scoped `DysonToolPolicyStore`, `DysonPluginCatalogService`, `IDysonPluginPackageService`, `DysonPluginLifecycleService`, protected-variable and hook-review services, `ThemeService`, singleton `HttpClient` (default `IHttpClientFactory` client, including `XaiGrokRequestHandler`; process lifetime so an adopted session survives circuit dispose), `ManagedInferenceProviderCatalog` (CLIProxy `All` plus direct OpenRouter / OrcaRouter `Direct`), `DysonUiHost`; singleton `DysonMessageBus` then `DysonSessionEventPublisher` next to `DysonSessionRuntimeRegistry` + `IDysonSessionRuntimeScopeFactory` (`DysonUiSessionRuntimeScopeFactory`); scoped `DysonUiRuntimeAttachment`, `IDysonAgentSessionRuntimeFactory` (`DysonUiAgentSessionRuntimeFactory`), `DysonUiAgentSessionRuntimeConfigBuilder`, and `DysonSessionRuntime` (resolved inside the retained subject scope, not the Blazor circuit); singleton `DysonPluginContributionResolver`, `DysonPluginPackageLimits`, and `IDysonPluginPackageParser`. Singletons also include `DysonCliProxyHost` (disposed on app shutdown) and `DysonAppUpdateService`. The registry is disposed on `ApplicationStopping`.

**Windows only:** `DysonUiWebHost` also registers `AddSingleton<IDysonBrowserControl, DysonCefBrowserControl>()`. `DysonUiHost` injects that singleton into every `DysonAgentSessionConfig.BrowserControl` it builds (new + resume) and subscribes to `SnipCaptured` so browser chrome snips become pending composer images. The retained-scope `DysonUiAgentSessionRuntimeConfigBuilder` assigns the same singleton when it is registered, and leaves `BrowserControl` null when it is not. When set, the engine MCP catalog includes browser tools (`OpenBrowser`, …) that open in-process CefSharp WPF windows. Continuous **win-x64** zips ship `DysonHarness.exe` from `DysonHarness.UI.Windows` — see [packaging/webview](../packaging/webview.md) and [releases](../packaging/releases.md).

On first open, a default **Demo Mock** provider + slug is seeded if none exists. SQLite lives under the platform app-data folder for the current `DysonAppMode` (see [storage/models](../storage/models.md)).

### Host log and circuit errors

Local hosting (`DysonHostingMode` ≠ Cloud) enables `CircuitOptions.DetailedErrors` for both browser `dotnet run` and the desktop CEF shell so the browser console receives CLR type/stack on a circuit fault. Cloud keeps `DetailedErrors` off. Windows CEF does not set `ASPNETCORE_ENVIRONMENT=Development`, so this is set in code from hosting mode — not Development-JSON-only.

`CircuitOptions.JSInteropDefaultCallTimeout` is 2 seconds (`DysonCircuitJs.Timeout`). Circuit code calls JS through `DysonCircuitJs`, which applies that cap even when the caller passes `CancellationToken.None`, and swallows cancel, disconnect, and JS-not-ready so those failures do not terminate the circuit. Do not call `NavigationManager.NavigateTo` — a canceled navigation invoke is fatal in the framework. Use `DysonCircuitJs.NavigateAsync` (`dysonNav.go` → `Blazor.navigateTo`). The home splash may wait up to 10 seconds for `dysonBoot.waitUntilResponsive`; that call passes its own cap.

`DysonAppPaths.GetLogFilePath(mode)` is `{root}/dyson.log` (sibling of `dyson.db`). The UI MEL `ILoggerProvider` writes **Error** and **Critical** only (UTF-8) and keeps the newest 5000 **physical** lines. On this branch (`DysonDev`) open `%LocalAppData%\DysonDev\dyson.log`. That file is the host/framework exception log — not the rail **Session log**, which is the structured `session_logs` timeline (see [sessions.md](../storage/sessions.md)). Rail rows are classified from line text by `DysonSessionLogDisplay` (Facts in `Harness.Tests`): Error needles include `openai api` so `OpenAI API 400 …: {body}` is an error badge (compact `retry` countdown lines stay warn).

`DysonUiHost` branches on effective `ProviderKind` (see below): `demo` (no credentials) → `DemoDysonAgentSession`; `OpenAICompatible` → `OpenAiCompatibleAgentSession` (engine). Anthropic is not wired yet. OpenAI-compatible sessions expose in-process web search MCP tools (`FreeSearch`, `WebFetch`, …) via the engine catalog — see [engine README](../engine/README.md)#web-search--fetch-in-process. Web tools summarize **inside** the executor (`DysonWebSearchSummarizer`); optional summarizer slug from Settings → General (empty ⇒ session model via `SummarizerProvider` null). Assert coverage for search SSRF, session todos, file manager, PlanResult, Plan shell warning, long-running shells, and UI helpers lives in `Harness.Tests` (`dotnet test src/Harness/Harness.Tests/Harness.Tests.csproj`) — not UI startup.

**Provider routing:** session type follows the slug’s provider `ProviderKind`. Demo mode is for offline UI testing — `DemoDysonAgentSession` injects mock tools every turn (`read_file`, `grep`, `list_dir`) and mocks `RenameSession` only on rename-review turns (1, 9, 17, …), without calling an LLM. OpenAI-compatible providers call the real API and only run tools the model requests.

**Mis-tagged providers:** if a row has `ProviderKind = demo` but a Base URL or API key is set, create/save in **Settings → Models** coerces it to `OpenAICompatible`, and `ResolveProviderAsync` treats it as OpenAI-compatible at session start even before repair. Use **Repair mis-tagged providers** on the Models settings page for a one-shot DB fix of existing rows (does not run on startup; leaves **Demo Mock** unchanged).

## Meta agent page

`/meta/{WorkDirectoryId:guid}` find-or-creates **one root Meta Agent session per work directory**: `Host.FindExistingMetaAgentSessionAsync` reads the unfiltered repository roots list and `MetaAgentSessionLocator.SelectExisting` picks the newest root with `AgentMode == "Meta Agent"` (`LastActivityUtc`, then `CreatedUtc`); else `StartNewSessionAsync(DysonAgentModes.MetaAgent, …)`. That lookup is not the sidebar list. Already-focused live Meta Agent for that workdir is reused. The sessions sidebar (`DysonUiHost.ListSessionsAsync` on Home and this page) does not show the Meta Agent row. **Open full session** still focuses that session on `/`.

Three columns (`MetaAgent.razor.css`): plans 260px | chat | Agents/Files tab strip 260px. Agents is selected when the page opens; Files mounts `FileTreePanel` for the route work directory (no `ActiveWorkRootPath`). Plans hide at `max-width: 1400px`; the right column (both tabs) hides at `1100px`.

The visual layout comes from the plan 159 refresh:
- **Feed and composer.** Both are centred at max 880px. The composer is a raised card with a round Send button; the hint sits below the card.
- **Messages.** Agent messages are unboxed with an avatar. User messages are an accent bubble, and the "You" label is sr-only.
- **Top bar.** Header actions are ghost icon buttons. Below 1280px the labels become sr-only, so the bar is icon-only and the labels survive as accessible names.
- **Agent cards.** `SubagentCard` and `MetaAgentChildRow` carry `data-status` (the `DysonSubagentStatus` text) and `data-running` (present only while running). CSS uses those for the status dot, the running pulse, and the failed tint, with no extra C#. Nested rows draw a tree guide.
- **Plans column.** Plans are cards with status pills, and the header shows the plan count.

The chat is deliberately plain (`MetaChatFeed` / `MetaChatItems.Build`): user `Normal` turns (typed text, image thumbs, and file-name chips — not paths or URLs), injected `UserComment`s, and `DisplayInfo` (`PostConversationMessage`, or `PostUserQuestion` with an inner question card). A `DisplayInfo` row whose key starts with `a:` and arrives after the feed's first render reveals like an LLM stream at 80 tok/s (`MetaChatReveal`: `TokensPerSecond` 80 × `CharsPerToken` 4 = 320 chars/s, `CharStaggerMs` 3.125). [`wwwroot/meta-reveal.js`](../../src/Harness/Harness.UI/wwwroot/meta-reveal.js) wraps the already-rendered markdown graphemes (not the source) in fading spans, then unwraps them; question cards and action buttons stay hidden until that finishes. History, a reload, and a session switch are the first render and show at once. Posts over about 6000 graphemes (~19 s at 320 chars/s), and `prefers-reduced-motion`, show the text at once. The feed is `aria-live="polite"`, so the full text is announced once. A re-render does not restart a reveal that is running or finished. Submit answer locks the card; a reload shows the persisted answer with the controls disabled and the button gone. A host error stays on the card and leaves it unlocked. Tool calls, reasoning, and harness turns are not shown — header **Open full session** is the escape hatch (`ResumeSessionAsync` if needed, then `/`). There is no in-page expanded `ChatPanel`. Header **Tasks** (first action, left of **Open full session**, disabled unless the meta session is focused) toggles `SessionTodosModal` mounted at page root immediately after `FileViewerOverlay`, outside `AppShell` (`.meta-stage` is `overflow: hidden`). Header **Visualizations** (after Tasks, disabled unless focused) opens `SessionVisualizationsModal`. A `DisplayInfo` bubble with `VisualizationId` adds **View visualization**, which opens that same modal focused on the id; a missing id shows "Visualization not found." The modal is a three-column board (pending, ongoing, complete); cards keep display name, task code, and comments, newest sequence first inside each column; empty columns stay visible. It closes when the work-directory id changes. Home's `SessionTodoOverview` chip is unchanged. Action buttons on a post go through `Host.InvokeMetaConversationActionAsync`. Built-in `open_plan:`, `open_file:`, and `open_url:` keys open the plan viewer, the file viewer, or the OS browser; other keys use the in-memory map. A bad id, a path outside the work directory, a non-http(s) URL, an unknown key, or a failed func is `Result` text on the bubble and the message stays.

A parent-event continuation is kind `ParentEvent` (20). It stays in the session transcript and is not a meta-chat bubble. A posted message may relay the status. A question uses `PostUserQuestion`. Neither may name the event. The answer is a later user turn, and that turn still carries the parked event. The model is instructed to attach an open button for each plan, workspace file, or http(s) URL named in that message.

Text-only send while a turn is in flight still **injects** (`Host.InjectTurnComment`); text-only send while idle starts a new turn (`Host.PromptAsync(..., MetaAgent)`). A send that includes attachments uses `PromptAsync` so words and files stay on one turn. Queued messages render as pending bubbles at the tail (`.meta-chat__msg--pending`, `.subagent-card__spinner`, × via `Host.RemoveQueuedPrompt`). No modal queue panel on this page. Injected comments are not queued — they land in the running turn with no spinner. Queued bubble text is `QueuedPrompt.Text` (full instruction); `FirstLine` stays for the compact composer queue.

The meta composer accepts images and other files by paste, drop, and the + picker. The existing **Must connect S3 bucket** modal (`FileStorageConnectModal`) opens only for images; an uploaded image keeps no local file. Chat shows thumbs and file-name chips, not paths or URLs.

Push-to-talk: `PushToTalkButton` sits after the + picker (hold it or hold Ctrl+M in the box; the transcript is inserted at the caret; not installed links to `/settings/voice`). Same component as the full-session composer. While voice mode is on, the page passes `Disabled` so the two mics do not race. The hint under the box adds `voice mode: say the agent name`.

Voice mode: `VoiceModeButton` is mounted in `meta-composer__pickers` immediately after `PushToTalkButton`. It is not on `Composer.razor`. It reads `Host.Voice` — the one `DysonVoiceMode` held by the subject's `DysonSessionRuntime` (null off Windows); the circuit does not resolve it. Requirements are checked on init and again on focus or mouseenter, at most once every 2 s.

| State | Class | Title |
| ----- | ----- | ----- |
| Service missing | `voice-mode--off` | Voice mode needs the Windows app. |
| Requirements fail | `voice-mode--off` | The reason (each one points at Settings → Voice) |
| Ready, off | (none) | Voice mode: say the agent name, then talk. Click to turn on. |
| On, listening | `is-on` | Voice mode on. Say the agent name, then talk. Click to turn off. |
| On, wake heard | `is-on is-capturing` | Listening… pause 3 seconds to send. |
| On, speaking | `is-on is-speaking` | Speaking. Say the agent name to interrupt. |

Unavailable uses `aria-disabled="true"` and a no-op click, not the `disabled` attribute, so the tooltip still shows. `aria-pressed` is true while on. Turn on calls `StartAsync`, then `Host.SetMetaVoiceModeAsync(voice)` (attaches voice to every live root meta session; the host owns `MessageReady` / `Failed`). Turn off (click) calls `SetMetaVoiceModeAsync(null)`, which stops with `UserOff`. A ready transcript goes to the root meta session of the active work directory (`DysonWorkDirectoryFocus.ActiveId`) without focusing it; the text already starts with `[voice input] `. Voice survives session changes, Settings, Home, and work-directory changes; `Dispose` only unsubscribes `StateChanged`. A remounted button adopts `IsOn` and raises `OnChanged(true)`, so push-to-talk stays disabled. It is never persisted; restart starts off. While voice is on, Settings → Voice play and record (and wake-name record) refuse with an error so they do not take the shared device. A short quiet listen chime plays once per wake-name match (idle or barge-in); the existing accept chime plays only on submit. Loop errors go to `Host.ReportError`. Static mic styles live in `VoiceModeButton.razor.css` (ring when on, accent while capturing).

Under the box: **model slug + effort pickers** (`ModelSlugPicker` + `ComposerEffortPicker`, left of `Ctrl+Enter to send`). They write straight to the focused meta session — `Host.SetSessionModelSlugAsync` / `Host.SetSessionReasoningEffortAsync` — and are re-read from the host afterwards, so a rejected or deferred switch cannot leave a stale label. Both handlers no-op unless `IsMetaFocused` (the host is shared; the picker also auto-writes on load). Effort choices come from the selected slug's `ReasoningModes` via `ComposerEffortOptions.Build`, which keeps the current value listed even when the slug no longer registers it. Effort changes are rejected while a prompt is in flight and the message lands in the page banner. Context size has no stepper here — Meta Agent is pinned at 180K.

Halt: `ComposerStopMenu` → `StopAllExecution` (the only user-side brake for a dispatched fleet). `StopMetaAgentDrone` is an agent tool.

Right column: an Agents | Files tab strip (Agents selected on open, not persisted). Agents lists live `<SubagentCard PersistenceId="…" />` for each `Session.SubSessions` child (click navigates to `/`). Under each Agents-tab card, one level of that agent's own `SubSessions` as compact rows (mode icon, title, `#id`, step or terminal status, spinner while `Active`). No model text unless it differs from the card. Click navigates like the card (`/`). More than 3: a `Show all (N)` / `Show less` toggle (`aria-expanded`), remembered per drone in a page-level set for the page lifetime. Chat cards and the Subagents modal stay flat. Empty state "No agents yet". The old "Agents" section label is gone. Files is `FileTreePanel` for the route work directory.

Left column: `MetaPlanList` over `IDysonPlanRepository.ListAsync(includeArchived: true)` (database rows, not `.dyson/plans/` files), split on `ArchivedUtc` into the active list and a collapsed **Archived (n)** section (hidden when empty; not persisted; no Build button). Right-click an archived row → **Restore** (`RestoreAsync`, then publish `DysonPlansChangedEvent`; the subscriber refreshes). There is no delete in the UI; the agent's `DeletePlan` archives. Click a row → `Host.OpenMetaPlanAsync` (`GetAsync` + `OpenFileViewerContentAsync` with display path `metaplan:{planId}/{slug}.md`; never a filesystem read). **Build** (disabled while `Status == Building` or the Meta Agent runtime is not attached) → `Host.PromptMetaPlanBuildAsync`: inject if a turn is in flight, else `PromptAsync` so the agent itself calls `BeginBuildPlan(planId)`. UI does not spawn a drone and does not set `Status=Building`. Overlay footer **Build plan** is the same message. Comments reuse `DysonFileViewerComments.FormatPrompt` and `Host.PromptOrInjectAsync` (same inject-vs-prompt split as the meta composer). Building pills spin from `Status` only. Live refresh: subscribe to `DysonPlansChangedEvent` on `DysonBusScopes.WorkDirectory` (engine publishes after plan-tool mutations; a drone in another session is the usual writer). Host `Transcript | SessionGraph | Busy` still calls `RefreshAsync` as a harmless extra. Empty state keeps column width.

Engine behaviour: [meta-agent.md](../engine/meta-agent.md).

`SettingsLayout` nests under `MainLayout` (side nav: General, System, Voice, Analytics, Agent behavior, Models, File storage, Shells, Plugins, Agent modes, Back to agent). `MainLayout` also mounts `FileStorageConnectModal` next to `ConfirmDialog`.

## Chat markdown links

All absolute `http://` / `https://` links in chat turn markdown (assistant body, user prompt, harness instruction) and in the file/skill viewer markdown open in the **OS default browser**, not inside the Blazor/WebView host. `DysonUiHost.OpenUrlInDefaultBrowser` allows only http(s); `wwwroot/chat-external-links.js` (loaded from `App.razor`) intercepts clicks under `.turn-block__body`, `.turn-block__user-prompt`, `.turn-block__instruction`, and `.file-viewer-modal__markdown`. In-app routes (e.g. settings `<a href="/settings/…">`) are left alone.

## Work directories

- Boot: `Home` renders `SplashScreen` over the shell until `_booted` is true, so no control is clickable before workdirs/sessions exist. On first render `Home.OnAfterRenderAsync` runs `HydrateWorkDirectoryAsync` once (guarded by `_workdirHydrated`).
- Cold-boot cost is **client-bound, not server work**. Measured with per-step logging on a cold `dotnet run` + fresh browser: stored-id read ~25ms, `WorkDirs.GetAsync` ~10ms, and everything inside `RefreshGitBranchAsync` (`CreateLocalAsync` ~0-3ms, `DysonGitInfo.TryGetBranchAsync` ~80-205ms) completes in well under a second — yet the `await` on it does not resume until ~50-64s later, after which `RefreshSessionsAsync` adds ~10ms. The gap is the Blazor Server circuit dispatcher: render batches wait on acknowledgement from a browser whose main thread is still saturated by initial script load (first inline script ran ~7s after navigation), so queued continuations cannot resume. A warm reload of the same server runs the identical hydrate in **~95ms**. In one cold boot the prerender circuit finished hydrate in 330ms while the interactive circuit took 64s — same code, same DB, same git.
- Consequently the splash also waits for the client itself: `Home.WaitForClientResponsiveAsync` calls `dysonBoot.waitUntilResponsive` (`wwwroot/theme.js`), which resolves on `requestIdleCallback` (double-rAF fallback) and is capped by `ClientReadyMaxWaitMs` (10s). Without this the shell appeared but swallowed clicks for several seconds after the splash left.
- UI awaits `TryGetBranchAsync` / `TryGetStatusPorcelainAsync` / `DysonSessionWorktree.*Async`. Do not call sync git from the circuit. Circuit code must follow [rules/rules_blazor_circuit.md](../../rules/rules_blazor_circuit.md). Stored-id boot still does not *await* the branch chip: branch/origin/`TouchOpenedAsync` all run from `CompleteBootMetadataAsync` after the splash dismisses so a dispatcher hop cannot pin the splash.
- Hydrate runs only on the **interactive** circuit (`RendererInfo.IsInteractive`). Prerender is a second `Home` instance; hydrating it duplicated git/DB work and left the interactive circuit waiting on a busy dispatcher (logs showed one pass at ~330ms overlapping another at ~64s).
- Bookkeeping writes returning an error Result on SQLite busy/locked instead of throwing is **robustness hardening, not the cause fix** — measurements show the SQLite steps at ~10-60ms, never the bottleneck.
- Active workdir id in `localStorage` key `dyson-workdir`
- Session list filtered by `WorkDirectoryId`
- Composer / header branch chip from `DysonGitInfo.TryGetBranchAsync` on the **focused session** path (bound worktree if set, else registered `AbsolutePath`)
- Files / Git rails cache `(WorkDirectoryId, normalized path)` so two sessions on the same workdir (main tree vs worktree) do not reuse one tree
- Long-running shells badge/list filter by focused session cwd when set
- Details: [storage/work-directories.md](../storage/work-directories.md)

## Plugin import

Composer slash **`/plugins`** opens `PluginModal` and clears the command/remainder without starting inference, including when ordinary composer attachments are pending. The modal currently has one **Import** tab:

1. Choose one source: browser-uploaded ZIP, host-native folder, or GitHub `owner/repo` / HTTPS URL with optional ref and plugin subdirectory. ZIP size is checked before buffering; local folders are copied to staging. GitHub refs are resolved to an immutable commit.
2. **Preview import** validates the staged package and shows format, identity/version/schema, source/commit/checksum, components, executable/network/hook/variable capabilities, unsupported items, and diagnostics. Preview/install never execute hooks, scripts, skill resources, commands, or stdio MCP.
3. Choose exactly one unselected scope: **Install for this project** (disabled without an active work directory) or **Install globally** (current app mode/user). Exact package and `PLUGIN_DATA` destinations are displayed.
4. Acknowledge the capability review, then install. Back returns to the retained preview without reacquiring the source. Multi-package Cursor repositories expose an inline subdirectory picker.

Installed packages contribute only through the effective global + active-project catalog. Skills enter the skill catalog/`LoadSkill`; always-apply rules enter the bounded session prompt; custom agents are explicit choices; `/plugin-{plugin}-{command}` selection inserts editable instructions rather than sending them automatically. The import UI does not mutate `openrules.json` or create `.dyson/mcp` files.

**Installed-plugin management:** **Settings → Plugins** lists the effective global + active-project catalog, retains shadowed global installations for inspection, and displays scope, source, version, capabilities, component inventory, diagnostics, and lifecycle status. It supports enable/disable and explicit uninstall with an independent retain/delete `PLUGIN_DATA` choice. Declared variables use the protected value service and only show `[SET]`/`[NOT SET]`, never plaintext. Hook review status and its constrained review controls are shown per supported hook; updates remain unavailable because no safe update lifecycle API exists. Plugin MCP activation remains default-deny and has no management UI. OpenAI `.app.json` components are shown as unsupported.

## Motion

**Tokens** (`:root` in `app.css`): durations `--motion-instant` 90ms, `--motion-fast` 140ms, `--motion-base` 200ms, `--motion-slow` 240ms, `--motion-pulse` 2400ms (running-status halo), with `--motion` kept as an alias of `--motion-fast` for existing rules. `--motion-instant` / `-fast` / `-base` mirror `DysonTransition` `EnterMs` / `ExitMs`, so do not change them. Easings: `--ease` (ease-out, the default), `--ease-in` (exits), `--ease-standard` (symmetrical/position changes), `--ease-spring` (small overshoot, for pops only). Target runtime is Chromium 149 (CefSharp), so `@starting-style`, `transition-behavior: allow-discrete`, and `interpolate-size: allow-keywords` are available.

**Reduced motion.** The blanket `@media (prefers-reduced-motion: reduce)` rule in `app.css` still kills every CSS animation/transition with `!important`, so anything declarative is safe by default. It carves out the busy spinners (`.turn-block__spinner`, `.subagent-card__spinner`, `.composer-stop__spinner`, `.skill-search-modal__spinner`) at a slower rate, because a frozen ring reads as broken rather than working. The `dyson-status-pulse` halo (running agent cards and tool rows) is deliberately **not** carved out, so it freezes and the static status dot remains. It does **not** cover motion orchestrated outside CSS, and the preference also suppresses `transitionend` / `animationend` — JS/C# sequences must ask `dysonUi.prefersReducedMotion()` (`theme.js`) and collapse their own duration to zero.

**`DysonTransition<TItem>`** (`Components/Motion/`) is the deferred-unmount wrapper for exit animations. Overlays here are `@if`-gated, so the node leaves the DOM before CSS can animate it; render the overlay inside `DysonTransition` instead. It caches the last set `Item` through a **timed** exit window (`ExitMs`, zero under reduced motion — never an event), and hands `ChildContent` a `DysonTransitionContext<TItem>` with `Item`, `StateClass` (`is-entering` → `is-entered` → `is-exiting`) and `IsExiting`. `OnEntered` fires after `EnterMs` for deferred focus (so `FocusAsync`'s scroll-into-view does not interrupt the enter), and `RestoreFocus` captures/restores the previously focused element via `dysonUi.captureFocus` / `restoreFocus`. Re-showing an item mid-exit cancels the unmount and returns to `is-entered` so CSS reverses from wherever it is.

**Two rules when consuming it.** Both are easy to get wrong and both fail only during the exit window, which is why they are called out:

1. **Render the child unconditionally.** Drop the component's own `@if` — the wrapper *is* the gate. An `@if` inside `ChildContent` re-creates the original bug, because the markup disappears before the exit animation can run.
2. **Read `ctx.Item`, never the source field.** During the exit window the source (`ConfirmDialogService.Current`, an `IsOpen` parameter, a host getter) is *already* null/false; only the wrapper still holds the value. Touching the source instead throws or renders empty for the length of the window. For the same reason, guard click/submit/keydown handlers with `!ctx.IsExiting` so a click landing on a fading overlay cannot re-fire the action it just closed.

31 surfaces use it — every `@if`-gated modal, overlay, popover, menu and toast in the app (inventory and per-surface notes are in the plan). `ReconnectModal` is the exception: it already animates both ways with native `<dialog>` + `transition: display allow-discrete` and was left alone.

**Shared classes** in `app.css`, applied additively next to a component's existing backdrop/panel classes: `.dyson-fade` (opacity only), `.dyson-fade-scale` (on a backdrop: fades it and lifts its element child panel), `.dyson-pop` (on a popover panel; set `--dyson-pop-origin` to match the anchor). They stay global because consumer components apply them to their own markup and because Blazor does not rewrite `@keyframes` names — see [rules/rules_ui_css.md](../../rules/rules_ui_css.md) for what else must stay in `app.css`.

Which one to reach for:

| Class | Goes on | Used by |
| ----- | ------- | ------- |
| `.dyson-fade-scale` | the **backdrop** element; its single element child is treated as the panel and lifted | the 20 dialog/overlay backdrops |
| `.dyson-pop` | the **panel** itself; set `--dyson-pop-origin` to match the anchor edge (`bottom center` for an upward picker, `top left` for a mouse-positioned menu) | the 5 popovers/menus, at `ExitMs="90"` (`--motion-instant`) |
| `.dyson-fade` | any element that only needs opacity | the 6 backdrop-less popovers, toasts and inline surfaces |

Two more global keyframes come from the UI refresh. `dyson-msg-in` (opacity + 6px rise) is applied only to the newest three meta feed items, so a history load does not cascade. `dyson-status-pulse` (opacity + scale on a pseudo-element) is the running halo used by `SubagentCard` and `.tool-status.working`. Neither one sits on a sticky ancestor.

`@keyframes dyson-fade-in` plus `.dyson-stream-chunk` are the two global animation hooks for the transcript. The keyframe is opacity-only because its consumers (`.turn-block--enter`, `.turn-block__body--final`, `.chat-panel__turns--swap`, `.settings-shell__content--enter`) all sit on or above `position: sticky` elements, where a `transform` would create a containing block and break pinning.

**Turn bodies are always mounted.** `TurnBlock`'s body is no longer `@if (IsExpanded)`-gated; it is a permanent `.turn-block__collapsible` wrapper whose `height` animates between `0` and `auto` (`interpolate-size: allow-keywords`), with `inert` keeping a collapsed body out of the tab order and the accessibility tree. Two consequences worth knowing:

- **It fixed the collapse storm.** `RebuildCollapsedDefaults` used to destroy every prior turn's subtree on each new prompt and rebuild it on re-expand, re-running `TurnBlock`'s JS attach/detach (tools resizer, `dysonStickyHeader`). Collapsing is now a pure class flip.
- **It costs DOM and render work.** Every turn's body now exists at all times and re-renders on every `ChatPanel` render (~13/sec while streaming, per the two nested 75ms coalescers). Collapsed wrappers carry `content-visibility: auto`, which skips their layout and paint but *not* the C# render pass. That declaration is deliberately scoped to the collapsed state only: `content-visibility` implies `contain`, which would break the sticky `.turn-block__main` / `.turn-block__tools` if it were ever active while expanded. The upgrade path, if a long session gets heavy, is a `ShouldRender` fingerprint on `TurnBlock` (there is a `ponytail:` comment on the rule) or mounting only recent turns.

The wrapper uses `overflow: clip`, **not** `hidden`. `hidden` would make it a scroll container, and that container would become the scrollport for the sticky columns inside it, breaking their pinning. `clip` clips without creating one. Do not "fix" this to `hidden`.

**Live Meta Agent posts** use [`wwwroot/meta-reveal.js`](../../src/Harness/Harness.UI/wwwroot/meta-reveal.js) (`window.dysonMetaReveal`), separate from streaming. The post is already rendered markdown. `paint` wraps each grapheme cluster (`Intl.Segmenter`, falling back to `Array.from`) in `.dyson-meta-reveal__char` (global, because JS nodes get no scope attribute) with a staggered `animation-delay`, then one timeout unwraps the spans and unhides `.meta-chat__question` / `.meta-chat__actions`. Opacity only, reusing `dyson-fade-in`. Whitespace stays a text node. Over about 6000 graphemes (~19 s at 320 chars/s), reduced motion, or a failed script shows the text at once (`ponytail:` in the script: spans unwrap at the end, so 6000 transient nodes is the ceiling; a longer post would need a recycled window). `MetaChatReveal.LiveKeys` decides live vs history; the first parameter set only fills the seen set.

**Streaming text** is painted by [`wwwroot/stream-text.js`](../../src/Harness/Harness.UI/wwwroot/stream-text.js) (`window.dysonStreamText`), not by Blazor. There is no CSS-only path: `StreamingPreview` materializes a fresh string per read and Blazor emits one `UpdateText` that reassigns a single text node, so there are no per-token elements to animate. Instead `TurnBlock` declares the streaming div with no text content and `dysonStreamText.paint(el, text)` appends whatever the new text adds beyond what it already painted as a `<span class="dyson-stream-chunk">` that fades in — Blazor never re-renders children it did not declare, so those spans survive its diffs. The Blazor-declared caret span sits in the same div, so chunks insert before it. Settled chunks are folded back into one text node on a **timestamp** check, never `animationend` (reduced motion suppresses that event), so a long stream does not grow one span per delta. A non-growth change (rewritten preview, restarted stream, recycled element) repaints from scratch rather than guessing.

*Fallback:* `TurnBlock` catches `JSException` from `paint`, sets `_streamTextUnavailable`, and re-renders with `@Turn.StreamingPreview` declared inline. If the module fails to load, streaming text still appears and updates — only the per-chunk fade is lost.

**Page, session and shell motion.** `.chat-panel__turns` crossfades on session switch, driven from `ChatPanel._renderVersion` rather than a `@key` (keying the element would cost its scroll and stick state); scroll happens first and the fade second, or the transcript visibly jumps after the fade lands. Per-turn entrance fades are gated on a seen-set so neither a session load batch nor the empty-state → timeline swap animates. `SettingsLayout` fades `.settings-shell__content` from a `LocationChanged` subscription, because settings → settings keeps `LayoutType` identical and only `@Body` swaps; crossing `/` ↔ `/settings/*` replaces the whole subtree including `MainLayout`, so that boundary gets an enter fade on `.page-root` only. Sidebar collapse and desktop rail close animate their `grid-template-columns` tracks (the rail keeps `display: none` but defers it with `transition: display allow-discrete`), gated behind the existing `app-shell--rail-hydrated` class so nothing animates on cold boot or during prerender.

**New CSS goes in `<Component>.razor.css`**, not `app.css` — scoped CSS is already wired through `Harness.UI.styles.css` in `App.razor`, so adding the file is the whole setup. The motion work added `AskQuestionPopover`, `ChatPanel`, `Composer`, `PlanReadyPopover`, `TurnBlock`, `SettingsLayout`, `StatusToast` and `DysonTransition` isolation files. The UI refresh (plan 159) added `Sidebar`, `SessionList`, `SubagentCard` and `SessionVisualizationsModal`. The `SubagentCard` and visualizations-modal blocks moved out of `app.css` whole. The `.subagent-card__icon--*` tints and `.subagent-card__spinner` stay global because `MetaAgentChildRow` reuses them. Tokens, `@keyframes`, the `.dyson-*` consumer classes, `MarkupString`-targeting rules and the `prefers-reduced-motion` block must stay global; existing `app.css` blocks are not bulk-migrated as drive-by work. Full rule: [rules/rules_ui_css.md](../../rules/rules_ui_css.md).

Converting fixes the "No OpenAI-compatible provider available for turn summarization." banner when the session provider was the cause (a non-OpenAI Settings summarizer slug still fails); while busy, validates then stashes the slug and applies it after the turn finishes (before draining the prompt queue) so the current turn stays on the old provider; with no session, updates pending effort for the next New session. **Engine** fallback (`Config.FallbackChatProvider`) is a different path: it mutates `session.Provider` mid-turn after retry exhaustion (or immediate 401/403) and persists the new slug/effort; the user picker still defers while busy (an explicit user pick flushed after the turn still wins)
- **Session effort:** `SetSessionReasoningEffortAsync(effort)` — overrides session `ReasoningEffort` / live provider only (not the slug default); empty omits the request field; persists when a session is focused; blocked while busy; New Session seeds from the current composer effort (live session when focused, else pending)
- **Session max target context:** `SetSessionMaxTargetContextTokensAsync(n)` — session override for the context-compaction limit (null inherit, `0` = Off, ±10K stepper in Composer footer; the tooltip says context is summarized automatically when it passes the limit); cascade session → slug `DefaultMaxTargetContextTokens` → 200K. **Meta Agent is pinned at 180K:** the host rejects changes (`"Meta Agent context is fixed at 180K."`) and Composer hides the ± stepper when `SelectedAgentMode` is Meta Agent (`ContextLimitLocked`). Meta Agent Drones keep the cascade. **Live chip:** `SessionOutgoingContextTokens` reads `DysonAgentSession.LiveContextTokens` — the live count while a turn runs (updated per request and per response), else the cached idle estimate (`CachedOutgoingContextTokens`, rebuilt off-thread via `RefreshOutgoingContextTokensAsync` at turn boundaries / session focus). After a full summary or context compaction excludes turns, the engine recomputes that estimate in the background and publishes it, so the chip drops right away instead of showing the pre-summary size until the next request. The host subscribes to `DysonSessionContextTokensChangedEvent` on `Wildcard`; the handler runs on the session loop thread, ignores other sessions and unchanged values, and only calls `Notify(Streaming)` (coalesced), so components still marshal through `InvokeAsync`. Models page sets slug default for managed slugs
- **Plan-ready sticky:** `PendingPlanReady` / `BuildPendingPlanAsync` — after latest `PlanResult` with a path, composer shows View / Build until a later `BeginBuildPlan` turn (layout-only: Recap + Agent actions + mandatory `CreateTodo` per action after `ReadFile`; no StartSubagent / WriteFile / shell / product work; non-Wait-consumed buffered Explore reports fold into that Instruction); legacy `[BuildPlan]` user turns still dismiss sticky. - **File viewer:** in-memory path is `RequestOpenFileViewerContent` → `OpenFileViewerContentAsync` (loading then `Task.Run` prepare); large/non-markdown in-memory bodies use preview-store `text/plain` iframe. No Git repo, no usable Git, no comparable `HEAD`, or annotation lookup failure → empty list and the file still opens as today (never replace a readable-file overlay with a Git error). PDF/image/pending/in-memory/`RequestOpenFileViewerContent` previews stay unannotated.

- **Todos:** host subscribes `TodosChanged` → `Notify()` (publishes host-scope `DysonHostStateChangedEvent`) so `SessionTodoOverview` refreshes without a full reload; MCP todo tools mutate the focused session’s own list
- **Subagents overview:** `SessionSubagentOverview` binds to `Session.SubSessions` (session-owned roster) and opens a modal of `SubagentCard`s from the overlay chip (instead of an inline expand); spawn-turn `SubagentCard`s remain under `TurnBlock`. - **Rename:** demo tool executor handles `RenameSession` → `RenameAsync` + persist `Title` + `SessionRenamed` log; host `SessionRenamed` notifies UI; Home overlays the focused sidebar title in-memory (no `ListSessionsAsync` on host-scope bus events)
